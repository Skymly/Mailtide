# 0.3 Create a Mailbox on an Account

## 产品句

The Person can create a Mailbox on an Account.

False on origin/main: Mailboxes only appear after IMAP LIST/sync. `IImapClient` has no create verb; the shell has no New Mailbox action.

## Non-goals

- Rename or delete Mailboxes
- Nested hierarchy UI or Person-chosen IMAP hierarchy delimiter
- Assigning Inbox / Sent / Trash / Junk roles (roles stay provider-synced on list)
- Gmail labels, Archive-as-All-Mail
- Entra, JMAP, macOS/iOS
- Android background sync, FCM, WorkManager
- Conversation threading in the UI (see 0.2 Worth exploring)
- Git tag / GitHub Release packing
- Avalonia control-tree tests

## Vertical slice

One implement ticket (hop D) crossing the layers that actually change:

1. IMAP port: create a Mailbox by path/name on the connected Account.
2. Core: `CreateMailboxAsync(accountId, name)` — IMAP create, then a local Mailbox row (no role). Reject blank names and duplicate paths on that Account.
3. BrowseShell + shared UI: New Mailbox when an Account is selected; reload Mailboxes.
4. Tests: Core + Desktop BrowseShell with the fake IMAP client. Live IMAP skipped unless a secret is already in the environment.

## Scope

In:

- `IImapClient` create + MailKit adapter + fakes
- `MailtideApp` create verb (not a pass-through module)
- BrowseShell + MailShellView
- Desktop tests

Out:

- New public Core module that only forwards the verb
- Per-minor `ready-for-human` 回归票

## Acceptance

- [ ] With an Account selected, the Person can create a Mailbox by name; it appears in that Account's Mailbox list.
- [ ] Blank name, or a name that already exists on that Account, is an error.
- [ ] IMAP failure does not insert a local-only Mailbox.
- [ ] Core + BrowseShell tests green. `.\build.cmd Test` green on the implement PR.
