# 0.4 Rename a Mailbox on an Account

## 产品句

The Person can rename a Mailbox on an Account.

False on origin/main: Mailboxes can be listed, created, and used as move destinations, but `IImapClient` has no rename verb and the shell has no Rename Mailbox action.

## Non-goals

- Delete Mailbox
- Nested hierarchy UI or Person-chosen IMAP delimiter
- Changing Inbox / Sent / Trash / Junk roles (roles stay provider-synced)
- Gmail labels, Archive-as-All-Mail
- Entra, JMAP, macOS/iOS
- Android background sync, FCM, WorkManager
- Conversation threading in the UI (still Worth exploring)
- Git tag / GitHub Release packing
- Avalonia control-tree tests

## Vertical slice

One implement ticket (hop D) crossing the layers that actually change:

1. IMAP port: rename a Mailbox by path.
2. Core: `RenameMailboxAsync(accountId, mailboxId, newName)` — IMAP rename first, then update local Name/Path. Reject blank names, missing Mailbox, duplicate name/path on that Account. Same name is a no-op.
3. BrowseShell + shared UI: Rename when a Mailbox is selected; reload Mailboxes.
4. Tests: Core + Desktop BrowseShell with the fake IMAP client. Live IMAP skipped unless a secret is already in the environment.

## Scope

In:

- `IImapClient` rename + MailKit adapter + fakes
- `MailtideApp` rename verb (not a pass-through module)
- BrowseShell + MailShellView
- Desktop tests

Out:

- New public Core module that only forwards the verb
- Per-minor `ready-for-human` 回归票

## Acceptance

- [ ] With a Mailbox selected, the Person can rename it; the new name appears in that Account's Mailbox list.
- [ ] Blank name, missing Mailbox, or a name that already exists on that Account is an error. Same name is a no-op.
- [ ] IMAP failure leaves the local Name/Path unchanged.
- [ ] Core + BrowseShell tests green. `.\build.cmd Test` green on the implement PR.
